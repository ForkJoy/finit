Glob Include 已知问题
=====================

背景
----

当前工作区修改为块格式 `include("pattern")` 和 legacy 格式
`include pattern` 增加了 POSIX `glob(3)` 通配符展开。普通 `*` 只匹配单个路径段，
不会跨越 `/`，因此不会自动递归子目录；`**` 也没有 shell globstar 的递归语义。
如需匹配一层子目录，必须显式写成 `/etc/finit.d/*/*.conf`。

本文记录当前实现保持不变时的已知问题。严重性综合考虑触发概率与影响范围。
这些问题都与本次修改涉及的代码路径相关，但不全是新根因：循环包含和 legacy
错误传播原本已有缺陷，长路径截断也已存在；本次 glob 支持增加了新的触发方式或
使后果更隐蔽。

问题清单
--------

### 1. 通配 include 可能递归包含自身

**反例：** `/etc/finit/self.conf` 包含 `include /etc/finit/*.conf`，匹配结果又包含
`self.conf`，于是配置不断读取自身，最终可能耗尽栈或文件描述符。

**严重性：高。** 可能导致 finit（通常是 PID 1）崩溃或系统启动失败；显式包含
自身原本也存在相同根因，但通配符让误触发更容易。

### 2. 块格式的多个匹配文件会被压入同一个 LIFO include 栈

**反例：** `include("/etc/finit.d/*.conf")` 匹配 `10-base.conf` 和
`90-override.conf` 时可能先解析 override 再解析 base；匹配 11 个普通同级文件时，
还可能被误报为 include 嵌套过深。

**严重性：高。** 常见配置数量即可触发，可能造成覆盖顺序颠倒、解析失败，或在
中途失败后留下不对称的 lexer 状态。

### 3. legacy 格式会吞掉真实 glob 错误

**反例：** reload 时系统内存紧张，`include /etc/finit.d/*.conf` 的 glob 展开返回
`GLOB_NOSPACE`，代码却按“没有匹配文件”处理并报告成功，相关服务可能因未重新注册
而被移除。

**严重性：中。** 触发条件较异常，但可能影响运行中的服务，而且错误会被隐藏。

### 4. 块格式也会吞掉真实 glob 错误

**反例：** `include("/etc/finit.d/*.conf")` 因内存不足或目录读取错误而展开失败，
主配置仍可能被认为解析成功，实际却没有加载目标配置。

**严重性：中。** 正常环境下不常触发，但会让系统带着不完整配置继续启动或 reload。

### 5. 块格式不再优先按字面文件名处理 glob 元字符

**反例：** 磁盘上确实存在 `unit[1].conf`，配置写
`include("/etc/finit.d/unit[1].conf")` 时，`[1]` 会被解释成字符类，可能改为加载
`unit1.conf`，或者遗漏真正的目标文件。

**严重性：低。** 这是兼容性回退，但包含这些字符的配置文件名较少见。

### 6. legacy 格式也不再优先按字面文件名处理 glob 元字符

**反例：** 原本要包含字面文件 `service?.inc`，当前实现会将 `?` 解释为通配符，
转而加载 `service1.inc`、`serviceA.inc` 等文件。

**严重性：低。** 触发场景罕见，但可能意外加载并启动非目标服务。

### 7. legacy 通配结果没有排序

**反例：** `10-base.conf` 提供基础设置，`90-override.conf` 提供覆盖设置；文件系统若
先返回 `90` 再返回 `10`，基础设置反而最后生效。

**严重性：中高。** 数字前缀控制加载顺序是常见用法，而文件系统枚举顺序不受保证，
同一配置可能因目录重建或文件系统变化而得到不同结果。

### 8. 块格式通配结果同样没有排序

**反例：** `10-base.conf` 设置 `runlevel = 2`，`90-override.conf` 设置
`runlevel = 3`，未排序的加载顺序可能让最终值变成 2。

**严重性：中高。** 配置一旦依赖后加载覆盖前加载，结果便不可复现。

### 9. 块格式可能失去原有的 `~` 展开能力

**反例：** `$HOME/extra.conf` 存在，原有 `include("~/extra.conf")` 可以加载；当前
实现先调用未启用 `GLOB_TILDE` 的 `glob()`，可能直接报告文件不存在。

**严重性：低到中。** 系统配置通常使用绝对路径，但已有部署若依赖该行为，升级后会
直接解析失败。

### 10. legacy 通配成员解析失败后，整体仍可能报告成功

**反例：** `*.conf` 匹配三个文件，前两个成功生效，第三个有语法错误；父级
`legacy_parse_conf()` 最终仍返回成功，系统带着只加载一部分的配置继续运行。

**严重性：高。** “部分生效但报告成功”会造成难以发现的不一致；错误传播根因原本
已经存在，本次多文件 include 让该场景更容易发生。

### 11. 块格式依赖 libconfuse 的非公开符号

**反例：** 开发机上的 libconfuse 恰好导出 `cfg_lexer_include()`，构建成功；换到另一个
同样满足声明版本要求、但只导出公共 API 的发行版后，最终链接报
`undefined reference to cfg_lexer_include`。

**严重性：中高。** 固定构建环境可能暂时无影响，但跨发行版、动态链接或库升级时
存在明确的构建兼容性风险。

### 12. 很长的 legacy include 路径可能被截断并静默遗漏

**反例：** include 模式超过 `CMD_SIZE - 1`，路径被截断；若截断后的内容仍含 `*`，
glob 即使没有匹配文件，也可能不报错并返回成功。

**严重性：低。** 超长实际路径很少见；固定缓冲区截断原本存在，本次判断使部分失败
从明确报错变成静默成功。

### 13. 特定 glob 错误路径可能泄漏内存

**反例：** 某些 libc 在 `GLOB_NOSPACE` 或 `GLOB_ABORTED` 后保留部分已分配结果，
无通配符的 legacy 错误分支却在 `globfree()` 前返回；异常条件下反复 reload 会逐步
累积泄漏。

**严重性：低。** 需要特定 libc 行为和异常环境，单次泄漏通常有限。

建议优先级
----------

1. 优先处理循环 include、块格式 LIFO/include 深度、legacy 错误传播问题。
2. 恢复确定的排序，并避免依赖 libconfuse 私有 ABI。
3. 用统一 glob 辅助函数集中处理真实错误、清理、字面路径和长路径问题。
4. 若暂不兼容字面 glob 元字符或 `~`，应明确记录为语法限制并给出清晰错误。
